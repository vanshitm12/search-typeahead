# Search Typeahead System

A working search-typeahead (autocomplete) system with a distributed cache,
consistent hashing, recency-aware trending, and batched writes. Built for the
HLD101 assignment. Single Python process, in-memory, runs with one command.

![suggestions](docs/screenshot_suggestions.png)

---

## 1. What it does

When you type in the search box it suggests up to 10 popular queries matching
your prefix, sorted by popularity. Submitting a search records it (so popular
queries get more popular), and a "Trending now" section surfaces what's hot
*recently*. Under the hood it demonstrates the four ideas the assignment grades:

| Idea | Where | Marks |
|------|-------|-------|
| Prefix search via a **trie** with cached top-K per node | `app/trie.py` | core |
| **Distributed cache** + **consistent hashing** for node ownership | `app/cache.py`, `app/consistent_hashing.py` | 60% |
| **Trending** via recency-decayed scoring | `app/store.py` | 20% |
| **Batch writes** that aggregate before persisting | `app/batch_writer.py` | 20% |

## 2. Quick start

```bash
# 1. Install dependencies
pip install fastapi uvicorn

# 2. (Optional) regenerate the dataset — a copy is already in data/queries.csv
python generate_dataset.py

# 3. Run the server
python -m uvicorn app.api:app --host 127.0.0.1 --port 8000

# 4. Open the UI
#    http://127.0.0.1:8000
```

The first startup loads ~120,000 queries and builds the trie (about 7 seconds),
then prints `Loaded 120,000 queries`. After that, suggestions are instant.

### Run the tests / benchmark

```bash
python test_e2e.py     # verifies every endpoint and edge case
python benchmark.py     # prints the performance report numbers
```

## 3. Dataset

`data/queries.csv` has **120,000** distinct `(query, count)` rows (the minimum
required is 100,000), generated by `generate_dataset.py`. Counts follow a
Zipf-like distribution (a few very popular queries, a long tail of rare ones),
which mirrors real search traffic. Format:

```
query,count
iphone,100000
iphone 15,85000
java tutorial,40000
```

To use your own data, replace the file with the same two columns and restart.

## 4. Architecture

```
                 ┌──────────────────────────────────────────────┐
   Browser  ───▶ │  FastAPI (app/api.py)                         │
   (static/      │                                               │
    index.html)  │  GET /suggest ─┐                              │
                 │                ▼                              │
                 │        ┌───────────────┐  miss   ┌──────────┐ │
                 │        │ Distributed   │────────▶│  Trie    │ │
                 │        │ Cache         │◀────────│ (top-K   │ │
                 │        │ (4 nodes,     │  fill    │  per node)│ │
                 │        │  TTL, routed  │         └──────────┘ │
                 │        │  by ring)     │              ▲       │
                 │        └───────────────┘              │rebuild│
                 │             ▲ consistent hashing       │       │
                 │             │ picks owning node         │       │
                 │  POST /search                           │       │
                 │     │ dummy "Searched" (instant)        │       │
                 │     ▼                                   │       │
                 │  ┌───────────────┐  flush   ┌──────────────────┐│
                 │  │ Batch Writer  │─────────▶│ Query Store      ││
                 │  │ (buffer +     │ aggregate│ (count +         ││
                 │  │  aggregate)   │          │  recency_score)  ││
                 │  └───────────────┘          └──────────────────┘│
                 └──────────────────────────────────────────────┘
```

**Read path** (`GET /suggest`): cache first → on miss, read the trie, fill the
cache, return. The trie stores a precomputed top-10 list at every node, so a
lookup is O(prefix length), independent of dataset size.

**Write path** (`POST /search`): returns `{"message": "Searched"}` immediately
and hands the query to the batch writer. A background thread flushes aggregated
increments into the store every 2 seconds (or when the buffer fills), rebuilds
the trie, and invalidates affected cache prefixes so suggestions refresh.

See [`docs/DESIGN.md`](docs/DESIGN.md) for the full reasoning and trade-offs.

## 5. API documentation

| Method & path | Purpose | Behaviour |
|---------------|---------|-----------|
| `GET /suggest?q=<prefix>` | Fetch suggestions | Up to 10 prefix matches, sorted by score desc. Returns `{prefix, suggestions, source, latency_ms}`. `source` is `cache` or `trie`. |
| `POST /search` `{"query": "..."}` | Submit a search | Returns `{"message": "Searched"}` and records the query via batching. |
| `GET /trending` | Trending searches | Top queries by recent (time-decayed) activity. |
| `GET /cache/debug?prefix=<p>` | Inspect routing | Shows which cache node owns the prefix and HIT/MISS. |
| `POST /admin/ranking?mode=basic\|enhanced` | Switch ranking | `basic` = count only; `enhanced` = recency-blended. Same `/suggest` API serves both. |
| `GET /stats` | Metrics | Latency p50/p95/p99, cache hit rate, write-reduction ratio. |

Example:

```bash
curl "http://127.0.0.1:8000/suggest?q=iph"
curl -X POST "http://127.0.0.1:8000/search" -H "Content-Type: application/json" -d '{"query":"iphone 15"}'
curl "http://127.0.0.1:8000/cache/debug?prefix=iph"
```

## 6. Performance report

Measured via `benchmark.py` (5,000 suggest requests with realistic repeats,
3,000 search submissions on a 120k-query dataset):

| Metric | Result |
|--------|--------|
| Suggest latency p50 / p95 / p99 | **0.011 / 0.014 / 0.045 ms** |
| Cache hit rate | **99.6%** |
| Cache distribution across 4 nodes | even (consistent hashing) |
| Search submissions → actual DB writes | **3,000 → 12** |
| Write reduction via batching | **99.6%** |

Sub-millisecond p95 because hot prefixes are served from the in-memory cache;
the trie only runs on a cache miss. Batching collapses thousands of repeated
search submissions into a handful of aggregated writes.
